# History formats and generated tests

The formats are append-only JSONL, but none is a fixed public interchange standard. The property tests in `src/harness/properties.rs` generate **entire files**, with randomized orders and repetition of the entries below, using `proptest`'s shrinking to find small failing histories. They check message order, extracted text, model attribution, and duplicate streaming snapshots against an independently constructed expectation. The deterministic examples remain as anchors for specific regressions. No finite generator can prove coverage of *every* possible future format or every permutation of an unbounded history.

## Codex rollout

Sources: [rollout persistence policy](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/policy.rs), [response item/content types](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/models.rs), and [turn context](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn_context.rs).

Top-level records include `session_meta`, `turn_context`, `response_item`, `event_msg`, `compacted`, and `world_state`. A `turn_context.payload.model` establishes the model for that turn. `response_item.payload` has tagged variants: `message` (user, assistant, developer/system), `agent_message`, `reasoning` (plaintext `summary` and optional `content`, or opaque encrypted content), `function_call`, `function_call_output` (string or structured content array), `local_shell_call`, and other tool variants. `input_image`/`input_audio` and encrypted reasoning are not readable text. The tests mix metadata, model changes, user/assistant messages, reasoning summaries, tool calls, shell actions, tool output in both shapes, and agent messages.

## Claude Code

Sources: [community JSONL schema](https://github.com/eidos-agi/claude-session-commons/blob/master/docs/jsonl-schema.md) and [Claude Code session examples](https://github.com/anthropics/claude-code/issues/9736). This format is not a stable public contract. Locally observed records include `user`, `assistant`, `system`, `attachment`, `progress`, `file-history-snapshot`, `queue-operation`, `ai-title`, and other UI records. `message.content` can be a string or blocks (`text`, `thinking`, `tool_use` with structured `input`, `tool_result` containing nested content, or nontext media). Assistant records carry `message.model`. Repeated records with the same `message.id` may be streaming snapshots; only the longest saved snapshot is counted. The tests mix these shapes and metadata, including system content, attachment text, and snapshots. Binary image content and metadata-only entries are ignored.

## pi v3

Sources: [session file format](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md) and [message types](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/message-types.md). A `session` header is followed by entries with `id`, `parentId`, and timestamps. `message` contains roles `system` (prompt `sections` and tool schema deltas), `user`, `assistant` (text, thinking, tool calls, explicit model), `toolResult`, `bashExecution`, or extension `custom`. `model_change` tracks the current model; `custom_message` contributes extension-provided context. `compaction`, `branch_summary`, `context_edit`, `usage`, `custom`, and navigation/metadata entries also exist. The generators vary model changes, ordinary messages, tool calls/results, system deltas, shell output, custom messages, and usage, compaction, branch-summary, context-edit, and extension-state entries in version-3 files with linear and branched parent links.

## Scope and limitations

These tests verify the **saved text** extractor, not provider token accounting. The parser scans saved entries rather than replaying the active branch's context, compaction checkpoints, or context edits; doing the latter would be a separate feature and would require different counting semantics. Repeated prompts sent to the API, encrypted content, binary media, and ephemeral events absent from JSONL cannot be recovered. New or unknown entry types are skipped; add a generator case whenever support for one is implemented. Run `cargo test` (or `PROPTEST_CASES=2000 cargo test harness::properties`) to explore more histories. Proptest regression seeds in `proptest-regressions/` replay past failures.
